## 两层规则体系

### 第1层 全局：`skills/hermes-code-agent/CONVENTIONS.md`
- 放 Skill 目录内，安装自带，随 git 分发
- 用户可改；Hermes bundled-skill user-modified 机制保证升级不覆盖已改文件
- 内容 = Aider 结构 × OpenCode 内容类型融合（见下）

### 第2层 项目：`<项目目录>/<项目名>.md`
- 规则文件放项目目录**里面**，跟项目走——mv 迁移整个目录一起搬，永不分离
- 命名：用户指定过的名字优先；否则取项目目录名；生成后以文件为准

## 入口检查协议（每次编程任务开始）

```
①检测项目目录
  ├─ 有 → 过
  └─ 无 → clarify："项目需要专属目录，建议 <workspace>/<项目名>/，确认？"
②检测 <项目名>.md
  ├─ 有 → 读取加载
  └─ 无 → 从模板生成初始文件（Skill 按项目技术栈代填内容）
齐全 → 静默通过零打扰；缺失才提问。
```

- 工作目录变更只发生在编程之外；每次任务开始读当下配置即可，无需迁移追踪

## CONVENTIONS.md 内容结构（六节骨架）

1. 通用纪律（所有项目，不可覆盖）← OpenCode 硬规则
2. 工具链约定 ← Aider 事实段 + OpenCode 明确性
3. 编码规范（命名/风格/语言）← Aider 核心
4. 提交纪律（格式/时机）← Aider 核心
5. 测试与验证要求 ← 两家共有
6. 禁区 ← OpenCode

项目层 `<项目名>.md` 用同一骨架，内容由 Skill 首次接触时按实际技术栈代填。

## 冲突与命名规则

- 层级冲突：项目层覆盖全局层（近者优先）
- 项目名来源：用户明确说过的 > 目录名 > 文件内固化的名字

## 对两家的净增优势（验收维度）

| 维度 | Aider 单独 | OpenCode 单独 | 我们 |
|---|---|---|---|
| 分节结构 | ✓ | 较随意 | 取 Aider |
| 规则作用范围 | ✗ | ✓ | 兼得 |
| 工具链事实段 | 简略 | ✓ | 更完整 |
| 加载机制 | 手动/启动 | 宿主注入 | 检测驱动自动+缺失生成 |
| 项目层规则 | 无 | 多级目录 | 每项目一文件跟项目走 |
| 首次接触新项目 | 空 | 空 | Skill 代填初始内容（独家）|
