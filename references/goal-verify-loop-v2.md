# 开发目标：测试反馈重试循环 v2（Aider × OpenCode 强强联合版）

> 状态：已定目标，未实施。Bob 于 2026-08-25 拍板作为该功能的开发目标。
> 政策合规：两个来源功能六家对标表内均有（Aider 智能报错加工 + OpenCode 强制循环），合成不违反"六家没有的不做"。

## 合成哲学

OpenCode 保证模型"不能不修"（意愿问题），Aider 保证模型"每次都拿到修得动的线索"（能力问题）。前者是裁判，后者是教练——用 OpenCode 的铁律跑循环，每轮用 Aider 的方式加工反馈。弱模型的两大死因同时堵住。

## 五段流程规则

### 第1段 三通道分流（Aider逻辑）
编辑后不直接跑测试，按失败类型分三条独立通道，各有处理方式和重试预算：
1. 补丁没打上 → 不碰测试，直接进定位救援
2. 打上了但静态检查报错 → 快速失败秒级返回
3. 静态干净 → 才有资格进测试
核心思想：越便宜的检查越靠前。

### 第2段 定位救援 did-you-mean（Aider独门）
补丁匹配失败时：拿补丁目标片段去源文件模糊搜索 → 找最接近真实内容 → 生成"你要找的 vs 文件里实际是"对照 + 上下文打包喂回。
实现：difflib 行级模糊匹配（Aider 用 tree-sitter，我们精度打九折可接受）。
范围收窄：第一版只做补丁通道；测试失败只做分类模板不做定位。

### 第3段 静态诊断前置（OpenCode LSP层）
测试前先过静态检查：Python 用 py_compile/ruff；其他语言用各自 build/lint 命令。
限制如实标注：不是 LSP，抓不到跨文件类型错误。

### 第4段 强制循环铁律（OpenCode纪律层）——开发目标形态
1. 报错即输入：加工后的错误作为正式消息注入下一轮
2. 分类预算：三条通道各自计数（补丁3次/静态3次/测试5次），互不侵占
3. 总闸保险：总轮数封顶烧穿即停
4. 同批测试连续3轮失败 → doom熔断换策略（已有）
Skill 形态限制（不可消除，如实标注）：无宿主进程接管对话流，"物理强制"降级为提示词纪律+退出码辅助；模型理论上仍可在红灯时谎报 done。

### 第5段 绿后落盘
全绿自动 commit 存检查点（autocommit 已有）。

## 实施评估结论（2026-08-25）

| 段 | 可行性 |
|---|---|

| 静态前置 | Python 全覆盖；其他语言靠 build/lint 补八成 |
