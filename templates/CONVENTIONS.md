# CONVENTIONS.md — 全局编程约定

> 本文件随 hermes-code-agent Skill 分发，位于 Skill 目录内。
> 用户可修改；Hermes 的 bundled-skill user-modified 机制保证升级不覆盖你的改动。
> 冲突规则：项目层 `<项目名>.md` 覆盖本文件的对应条目（近者优先）。

## 1. 通用纪律（所有项目，项目层不可覆盖）

- 先验证、后完成：任何"完成"声明必须以真实测试/lint/构建全绿为前提。
- 不确定就查证：不凭记忆猜测 API、路径、版本；先读文件或官方文档。
- 最小改动：一次只改一件事；不顺手重构无关代码。
- 错误输出是下一轮的输入：原样处理报错信息，不复述、不改写。
- 红线：绝不提交密钥/`.env`；绝不强推受保护分支；破坏性操作必须用户确认。

## 2. 工具链约定

- 优先使用项目已声明的工具链（package.json / pyproject.toml / Makefile / Cargo.toml）。
- 测试命令从仓库信号自动探测；探测不到才问用户。
- Python 项目优先用 `.venv/bin/python`；Node 用 npm scripts；有 Makefile 优先 make。

## 3. 编码规范（命名 / 风格 / 语言）

- 命名跟项目既有风格走；新代码不引入新的风格体系。
- 注释与文档语言跟随项目现状（中文项目写中文，英文项目写英文）。
- 不引入新依赖除非必要；引入前说明用途与体积代价。

## 4. 提交纪律

- 每个 green 检查点可自动 commit（hca_gate verify 绿后），message 格式：`<动词短语> (verify pass)`。
- 用户明确的提交要求优先于本约定。
- commit message 用祈使句、一行主题、细节放正文。

## 5. 测试与验证要求

- 修 bug 先复现（红测试），再修复到绿。
- 新功能必须有覆盖核心路径的测试；纯配置/文案改动可豁免但需明说。
- 静态检查（quickcheck）先行，秒级失败不进测试套件。

## 6. 禁区

- 不修改系统配置、不碰 `~/.ssh/`、`~/.aws/`、任何密钥文件。
- 不删除数据（rm -rf / drop / reset --hard）除非用户逐条确认。
- 不发布、不发消息、不打 tag 除非用户明确指示。
